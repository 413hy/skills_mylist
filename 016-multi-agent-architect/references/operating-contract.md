# 执行契约

## Hard Rules

- 先理解需求，再执行。不得把用户的简短指令直接扩写成未经确认的范围。
- 能从本地上下文、文档、代码、任务系统或用户提供材料中发现的信息，先发现再提问。
- 每次进入实施前，明确本轮目标、交付物、范围外事项和验证方式。
- 对最终产品、功能、脚本、demo、Agent、同步结果或 PR，必须执行真实场景自测。接口、函数、构建或命令跑通只能作为辅助证据。
- 失败项必须修复并复测；不能把失败项包装成“后续建议”后直接交付。

## Interaction Recipe

1. 识别任务类型：文档生成、代码实现、系统同步、学习引导、Agent 规划或多会话编排。
2. 读取当前 skill 的 `SKILL.md`、`references/workflow.md`，必要时读取 `references/original-prompt.md`。
3. 建立理解镜像：目标、约束、输入、输出、风险、验证方式。
4. 执行任务，并保持输出与本 skill 的 Output Contract 对齐。
5. 按 `references/scenario-validation.md` 执行代表性场景自测。
6. 交付时附上自测证据、未测项和阻塞项。

## Failure Handling

- 如果缺少测试账号、样例数据、目标系统权限或运行环境，先尝试从项目中发现；发现不了就明确列为阻塞。
- 如果真实场景自测失败，先修复或调整交付物，再重跑对应场景。
- 如果用户要求跳过自测，仍需明确说明跳过后残留风险。
- 如果任务本身只是计划、文档或提示词，也必须用一个小样例验证它能指导真实执行。

## Evidence Standard

自测记录至少包含：场景名称、输入数据/账号、操作步骤、期望结果、实际结果、结论。涉及浏览器或 UI 时，优先使用可见页面状态、截图、DOM 状态、日志或目标系统链接作为证据。
